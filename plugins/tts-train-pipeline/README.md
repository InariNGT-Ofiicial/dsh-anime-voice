# dsh-tts-train-pipeline

把**角色语料**做成 **GPT-SoVITS TTS 音色**（`.pth` + `.ckpt`）的 DSH 插件。

它是 `dsh-train-pipeline`（DDSP / SVC 音色）的**TTS 对偶**，不是它的升级版。
两者做的是不同的东西，不能互相替代：

| | dsh-train-pipeline（DDSP/SVC） | 本插件（GPT-SoVITS/TTS） |
|---|---|---|
| 输入 | 只要音频 | 音频 **+ 台词**（必须逐条对齐） |
| 产物 | 音色转换模型 | 能「念任意文本」的 TTS 音色 |
| 超长音频 | 按能量谷切开 | **绝不切分**，整条丢弃 |
| 监督信号 | 无文本 | 文本 → 音素 → 语义 token |

> ★ **不可逆**：TTS 不能反向用于 SVC，SVC 也不能反向用于 TTS。
> 想两个都要，就两条链路各跑一次，共用同一份解包语料。

---

## 1. 安装

```bash
dsh plugin add <本目录或包名>
```

`dsh` 启动时自动加载 `cordis.patch.yml`。路径**默认全空**，由 `src/config.js` 自动发现；
发现失败时跑 `tts_doctor`，会给出可直接粘的配置片段。

三种给配置的方式，优先级从高到低：

1. 工具参数（`tts_build({ expName, ... })` 之类）
2. `<本插件>/tts.local.json`（本机覆盖层，**不进 git**）
3. `cordis.patch.yml` / profile 的 `cordis.patch.yml`
4. 环境变量 `DSH_GSV_ROOT` / `DSH_TTS_ROOT` / `DSH_COVER_ROOT`

### 前置依赖

| 依赖 | 用途 | 缺了会怎样 |
|---|---|---|
| GPT-SoVITS 工程（含 `webui.py`） | 训练与推理的全部脚本与底模 | 什么都做不了 |
| 工程内的 `.venv`（torch 需匹配 GPU） | 跑预处理/训练/推理 | 什么都做不了 |
| ffmpeg + ffprobe | 转码、裁静音、探时长 | 出料（`tts_build`）失败 |
| pyyaml | 生成 s1 训练配置 | s1 不能训 |
| faster-whisper + large-v3 缓存 | **仅** ASR 兜底 | 无台词语料没法补标 |

★ **torch 与 GPU 算力必须匹配**：Blackwell（`sm_120`，50 系）配 `cu126` 会报
`no kernel image is available`，必须 `cu128`。`tts_doctor` 会直接判死这一条。

## 3. 核心立场：原文优先，ASR 兜底

语料本身带台词时（剧本、字幕、标注表），那是**引擎级的无损数据**；
ASR 是「重新听写一遍」——会丢标点、认错人名、写错汉字。日语里「はし」和「橋」听感相同，
ASR 写错汉字，模型就学错发音。

实测同一部 galgame（KrKrZ 引擎）：

| 取法 | 抽到条数 | 备注 |
|---|---|---|
| 在 `lines` 里找文本 | 102 条 | 只能捞到选项菜单 |
| 在 `scene.texts` 里找 | **3135 条** | 说话人齐全，语音命中率 **100%** |
| faster-whisper 回标 | —— | 完全不需要 |

所以 `tts_asr` 只在「真的没有任何文本」时才用。

### KrKrZ 剧本结构（`tts_script` 凭什么能抽到）

```
scene.texts[i][0]          → 说话人
scene.texts[i][2][0][1]    → 日文原文    ← 日文语音要的是这一列
scene.texts[i][2][2][1]    → 官方简中    ← 给人看的，不能拿去训日文语音
scene.texts[i][3][0].voice → 语音 ID
```

`lines` 里只有指令流（bgm / 立绘 / env），台词在场景级 `texts` 里被索引引用——
这就是为什么在 `lines` 里找文本只能捞到菜单。

## 4. 会在哪里踩坑（都是实测出来的）

### 4.1 裁静音：`stop_periods=1` 会截断句子

ffmpeg 的 `silenceremove` 里，**正的 `stop_periods` 不是「从末尾裁」**，
而是在「音频开头之后遇到的第一段静音」处就停止写入——也就是句内第一个停顿。

实测 `yos001_002.ogg`（4.20s）：

| 写法 | 输出时长 |
|---|---|
| 不裁 | 4.20s |
| `start_periods=1 + stop_periods=1` | **0.66s** ← 只剩开头两个字 |
| `start_periods=1`（只裁头） | 4.04s |
| `start_periods=1 → areverse → start_periods=1 → areverse` | 3.81s ⚠️ 句子保住了，但尾音被削（见下） |

后果不只是音质：被截短的句子会小于 `minSec` 而被整条丢弃。
修复前 630 条只出 28 条（1.96 分钟），修复后出 383 条（27.18 分钟）。

**⚠️ 但 `areverse` 方案也不是终解（2026-10-24 更正，此前这里标的是「✅ 正确」）。**
`areverse + silenceremove(start_periods=1)` 并不是「切在阈值上」，而是把尾部一段真实语音一起削掉。
实测 `yos001_001.ogg`：

| | 时长 | 尾部静音 | 收尾电平 |
|---|---:|---:|---:|
| 原声 ogg | 3.04s | 82ms | −42.6dB |
| 走 `areverse` 方案 | 2.64s | **0ms** | **+0.5dB** |

即每条都停在满电平。换 −55dB 阈值、`start_duration=0` 也一样。用这种数据训出来的模型会学成
「句子该在满电平处直接断」，推理时吞末字——芳乃线 383 条实测末三字完整念出率只有 **33%**、PER 0.197。

现在的做法是**只裁头 + 尾部保留原衰减 + 兜 0.16s 静音底**（`tts_build` 默认）：末三字 33% → **93%**、
PER 0.197 → **0.018**。同一批语料、同一套训练配置，差别只在音频怎么切。

`tts_build` 现在输出 `tail_stats`：收尾电平中位（真人自然收尾约 −24dB）、尾部静音中位、
以及收尾 > −12dB 的占比；后者超过三成直接判「句尾被切断」。`trimTail=true` 可以复现旧数据集，
但会打警告——那是已知缺陷，只用于和历史模型对齐。

### 4.2 默认 `minSec` 是 2.0，不是官方建议的 3.0

galgame / 番剧单句语音中位只有约 3 秒。实测芳乃 630 条：

| minSec | 可用条数 | 丢弃（过短） |
|---|---|---|
| 1.5 | 155 / 200 抽样 | 42 |
| 2.0 | 136 / 200 抽样 | 61 |
| 3.0 | 99 / 200 抽样 | 98 |

`tts_build` 会把时长直方图写进 `build.json`，并在丢弃量远大于出料量时给出建议。
素材充足时可以调回 3.0。

### 4.3 v2Pro / v2ProPlus 漏了 `2-get-sv` = 静默训废

上游 `webui.py` 里有一句 `if "Pro" in version`，命中时才多跑一步 `2-get-sv.py`，
产出 `7-sv_cn/<wav名>.pt`（说话人向量）。

缺了它不会报错。`module/data_utils.py` 是这么写的：

```python
try:
    spec, wav = self.get_audio(...)
    ssl = torch.load(f"{self.path4}/{audiopath}.pt")
    if self.is_v2Pro:
        sv_emb = torch.load(f"{self.path7}/{audiopath}.pt")   # ← 这里抛异常
except:
    spec = torch.zeros(1025, 100)          # ← spec / ssl / wav 一起变全零
    ssl  = torch.zeros(1, 768, 100)
    ...
    print("load audio or ssl error!!!!!!")
```

**spec、ssl、wav 会一起被换成全零继续训。** 训练能跑完、能出权重、能推理，
但音色是废的。所以 `tts_preprocess` 把它当固定步骤，`tts_run` 的前置校验把它当**硬阻断**。

### 4.4 日文语料的 `3-bert` 是空目录，这是正常的

`1-get-text.py` 里：

```python
if os.path.exists(path_bert) == False and lan == "zh":
    bert_feature = get_bert_feature(...)
```

只在 `lan == "zh"` 时才抽 BERT 特征。日文语料没有 `3-bert` 文件不影响训练。
别看到空目录就去"修"它。

### 4.5 后台训练必须 `PYTHONUNBUFFERED=1`

Python 对**非 tty 的 stdout 是块缓冲**（默认 8KB）。重定向到日志文件时：

- 训练跑了几分钟，日志还是 0 字节 → 看起来像没启动
- 崩溃 / 被 abort 时缓冲区**不会刷** → 真正的报错直接丢失

`src/execution.js` 的 `pythonEnv()` 统一加了这个变量。

### 4.6 预处理产物「已存在就跳过」
`1-get-text.py` 第 47 行：`if os.path.exists(txt_path) == False:`。
换数据集不先重置 `opt_dir`，就会**拿旧台词去训新音频**——最难查的一类错。

`tts_preprocess` 的 `force=true` 用**改名**而非删除来重置（移到 `_stale_<时间戳>/`）：
既强制重跑，又留了回滚余地。

### 4.7 训练进程的 cwd 必须是工程根

`s2` 的 `save_weight_dir`、`s1` 的 `half_weights_save_dir` / `train_semantic_path`
全是**相对路径**。换个 cwd 就会写到别处去，而且不报错。

### 4.8 list.txt 的格式是硬契约

```
wav名|说话人|语言|文本
```

- 必须**正好 4 段**，多一段少一段都会抛异常后跳过整句
- 文本里的 `|` 会被替换成全角逗号（否则解包错位）
- 语言必须在白名单里：`zh` / `ja` / `en` / `ko` / `yue`，**不在白名单会被静默跳过**

`tts_build` 出料后会核对行数，`tts_preprocess` 会比对「文本特征行数 vs list 行数」，
不一致时明确提示「有句子被跳过」。

### 4.9 超长音频只能整条丢弃

SVC 可以按能量谷切开；TTS **不行**——切了音频和文本就对不上了，监督信号错位比少几条数据更糟。
所以 `tts_build` 里 `maxSec` 之外的样本直接丢弃并计数（`build.json` 里有 `rejected_long` 样本）。

### 4.10 epoch 数小于保存间隔 = 退出码 0 但一个权重都没有

`tts_run` 的门禁看的是**权重文件真的出现**（glob `<exp>_e*_s*.pth`），不是退出码。

### 4.11 s2 存权重前必须存在 `logs_s2_<version>/`

`s2_train.py` 的 `save_checkpoint` 会用 `shutil.move` 写到
`<exp_dir>/logs_s2_<version>/G_<step>.pth`，但它**自己不建这个目录**——
建目录的动作在上游 `webui.py` 第 517 行（s1 的在第 611 行，不过 s1 自己会 mkdir）。

命令行直跑会在**保存权重那一刻**抛 `FileNotFoundError`，整轮训练白跑：

```
FileNotFoundError: [WinError 3] 系统找不到指定的路径。
: '1792411894.14.pth' -> 'logs/yoshino/logs_s2_v2ProPlus/G_233333333333.pth'
```

`tts_run` 在启动前统一 `mkdir -p` 四个目录（`logs_s2_<ver>` / `logs_s1` /
`SoVITS_weights_<ver>` / `GPT_weights_<ver>`），并在输出里列出新建了哪些。

### 4.12 `ref-lang` 给错 = 合成出静音

推理时 `prompt_lang` 必须与**参考音频的真实语言**一致。给它 `zh` 而参考音频是日文时，
模型拿到的语义 prompt 是错的，实测输出塌成 0.68 秒、`peak=0.003` 的静音，
而且**不报任何错**。

同一段日文参考音频、同一句日文目标文本，只改 `prompt_lang`：

| prompt_lang | 时长 | peak | rms |
|---|---|---|---|
| `zh`（错） | 0.68s | 0.0027 | 0.00018 |
| `ja`（对） | 4.84s | 0.3032 | 0.0420 |

所以 `tts_infer` 的 `refLang` 默认是 `auto`：先按参考台词的字符构成判（假名→ja、
谚文→ko、汉字→zh、拉丁→en），判不出才退到目标语言。输出里会写明「参考语言: ja（自动判定）」。

> 对照实验的做法值得记住：先拿**官方底模**跑同一句。底模也是静音 → 问题在推理路径；
> 底模正常而自训权重静音 → 问题在训练。这一步能省掉几小时的瞎猜。

### 4.13 ctranslate2 找不到 cuBLAS 时自动降 CPU

本机 torch 是 cu128（`cublas64_12.dll` 在 `torch/lib` 下），但 ctranslate2 不会去那里找，
ASR 会报：

```
RuntimeError: Library cublas64_12.dll is not found or cannot be loaded
```

★ 这个错误是**惰性**的：`WhisperModel(...)` 构造可能成功，到第一次 `transcribe()` 才抛。
所以降级逻辑必须包住转写调用，只包构造会漏。`asr_label.py` 会把设备降到 CPU + int8
并在 `deviceDowngraded` 里如实标出。ASR 本来只是兜底，慢一点可以接受，报错不行。

### 4.14 训练日志里 tqdm 的 `\r` 会让「一行」长达上百 KB

`tts_status` 读日志尾部时必须同时按 `\r` 切分并限制单行长度，
否则整个进度条被当成一行甩到界面上，真正要看的信息全被淹没。

### 4.15 欠拟合的权重会「念到一半跳字」，先调采样再谈加训

轮数不足时，`temperature=1.0 / top_k=15` 的默认采样会在长句中间**整段跳字**。
同一句、同一权重、只改采样（芳乃 2 轮权重，实测 ASR 回读）：

| 采样 | 回读片段 | avg_logprob |
|---|---|---|
| `t=1.0, k=15` | …ちらやね桃色の美しい…（中间整段丢失） | -0.254 |
| `t=0.6, k=5` | …綺麗に透き通った風を食べ、桃色の…（基本完整） | -0.105 |
| `t=0.6, k=5, split=cut0` | 同上，句尾更完整 | **-0.090** |

所以**乱读先降温度，别急着加训**。但采样只能缓解，不能扩展模型没学过的句式：
训练语料全是 galgame 短句时，文学性长句的句尾（如「〜できます」）仍会被吞。
那种情况只能加 epoch 或加语料。

### 4.16 `cut5` 分句会把句尾切丢，整段朗读用 `cut0`

`text_split_method=cut5` 按标点切小句，独立合成后拼接 —— 好处是长文本不崩，
代价是句间韵律不连贯、句尾容易被截。**十几秒以内的单段散文用 `cut0`（不切）**
更连贯；超过约 15 秒再回 `cut5`。

### 4.17 显存被别的进程占着时，训练会慢 6 倍且不报错

8GB 卡上实测：独占时 0.8~1.9 s/it，与另一个占 1.9GB 显存的任务并存时升到 **7.3 s/it**，
显存显示 7869/8151 MiB —— 溢到共享内存了，但训练不会报错，只会静静地变慢。
开训前先看 `nvidia-smi`；`batch_size` 调小**救不了**这种情况（激活省下的还不够抵消溢出），
要么等对方结束，要么换卡。

### 4.18 跨语言不是免费的：纯单语语料训出来的音色念不了外语

芳乃的语料是**纯日文**（383 条 galgame 台词）。用她念同一段中文散文，实测：

| 语言 | 结果 | avg_logprob |
|---|---|---|
| 日文 | 完整念出，仅句尾少「ます」 | -0.10 |
| 中文 `cut0` | 只念出前半句就停（5.58s / 应约 10s） | -0.136 |
| 中文 `cut5` | 两段都念完，但音全错（冰糖→兵团、晨光→成员） | **-0.418** |

`v2ProPlus` 底模本身是多语言的，但 s2 微调会把音素→声学的映射拉向训练语言。
**框架对、音全错**是最容易蒙混过关的失败：ASR 回读还能对上「结构」，人耳一听就废。

所以：**要哪个语言的音色，就用哪个语言的语料训**。真要多语言，得在 list.txt 里混入多语种
（`lang` 列填对应标记），而不是训完日文再指望它念中文。

### 4.19 ★ 跨语言的正解：s2 自训拿音色，s1 用底模拿发音

4.18 那个「音全错」并不是 s2 的锅。三组对照（同一句中文散文、同一参考音频、
全部 `t=0.6/k=5/cut5`）：

| 组合 | ASR 回读 | avg_logprob |
|---|---|---|
| A 底模 s2 + 底模 s1（零样本） | 我们即使没有足够的**冰糖**，也能尝到清晨的风，引下桃色的晨光… | -0.138 |
| **B 自训 s2 + 底模 s1** | 我们即使没有足够的**冰糖**，也能尝到清晨的风，**饮下**桃色的晨光… | **-0.146** |
| C 自训 s2 + 自训 s1 | 我们即使没有足够的**兵团**也能**成为赢下逃赛的成员**… | **-0.419** |

**病根在 s1，不在 s2。** s2 学的是「语义 token → 声学」，语义 token 本身语言无关；
s1 学的是「音素 → 语义 token」，音素是**分语言**的。芳乃的 s1 只见过日文音素，
于是把中文音素映射到了错的语义位置 —— 换成底模 `s1v3` 立刻正常。

而且换掉自训 s1 之后**日文也变好了**（不只是没退化）：

| 同一段日文散文 | avg_logprob | 句尾 |
|---|---|---|
| 自训 s1（2 轮） | -0.10 | 「〜ことができ」缺「ます」 |
| 底模 s1 | **-0.057** | 完整念出「〜ことができます」 |

**结论：s1 训得少（几轮）是纯负收益** —— 灾难性遗忘把底模的多语言能力削掉了，
母语也没学到精。要么 s1 训够（几十轮 + 足够语料），要么**干脆不训 s1**。

工具层对应：`tts_infer` 的 `gptMode`（`trained` / `base`），`tts_register` 可把它记进音色清单，
之后推理默认沿用。**跨语言音色请注册成 `base`。**

### 4.20 音色清单曾按「名字」查，但调用方传的是「实验名」

`findVoice(cfg, expName)` 只比对 `v.name`，而用户给音色起的名字通常是中文（「芳乃」），
实验名是 `yoshino` —— 于是永远查不到，且**不报错**，只是静默退化成「没有注册记录」。
表现是：注册表里明明写了参考音频，推理却说「未给参考台词（音色更不稳）」。

已改成 `name` 与 `expName` 双向匹配。教训：**按名字查表时，先确认调用方给的是哪一列**；
查不到要能看出来，不能静默降级。

### 4.21 ★ ASR 是筛子，不是裁判

用 ASR 回读判定「念对了没有」，最大的风险是**把裁判的错误当成事实**。

先看一个真实翻车：判定曾写成「只要开头 6 个字对得上就算一致」——

```js
const same = norm(asr.text).includes(norm(args.text).slice(0, 6));   // ← 假阳性
```

于是一句音全错的输出「**我们即使没有**足够的兵团也能成为赢下逃赛的成员…」
因为开头 6 字与原文相同，被判成「✅ 内容基本一致」。**前缀匹配对系统性错误完全失明。**

现在的判定在 `src/asr-gate.js`：全文字错率 CER + `avg_logprob` 双条件，两个都过才算数。
配套 `test/asr-gate.mjs` 用**真实回读样本**做回归（14 项断言）。

**但换掉阈值还不够，必须先确认这个裁判本身可信。** 问法：
「如果 ASR 对某个词天生不敏感，那念对的版本是不是也会被判错？」

实测（同一段中文，三档 beam）：

| 组 | beam=1 | beam=5 | beam=10 |
|---|---|---|---|
| 底模 s1（念对了） | 冰糖 · -0.140 | 冰糖 · -0.138 | 冰糖 · -0.138 |
| 自训 s1 | 兵团 · -0.416 | 兵团 · -0.419 | 兵团 · -0.417 |

- 「ASR 认不出冰糖」**被证伪**：同样的词，念对的版本三档都稳定认对。
- 自训 s1 三档稳定是「兵团」，说明**不是解码偶然**，音频里确实没有 /tang/。
- 用日文 ASR 交叉听：念对的中文能被转写出「足りない**冰糖**でも…」（汉字原样保留）；
  音错的那版被转写成「ご視聴ありがとうございました」—— 这是 whisper 听不懂时的典型幻觉。

**结论的口径要收窄**：能说的是「音频里没有发出 /tang/ 这个音」，
**不能**说「它念了兵团这个词」——那是把 ASR 的判读当成了 TTS 的事实。
人耳听到底是「带口音的冰糖」还是「别的音」，自动指标准不了，**最终裁判是人耳**。

**另一个反直觉结论：日文的字符级 CER 几乎没有信息量。**
ASR 输出「私たち / 綺麗 / 透き通った / 食べ」，原文是「わたしたち / きれい / すきとおった / たべ」——
同音不同表记在字符级全算错。实测：念对了 CER 就有 **30.5%**，句尾少两个「ます」是 **37.3%**，
只差 7 个百分点。所以日文阈值放宽到 0.45，只用来拦「大面积离谱」。

**所以「多次生成 + ASR 门」到底能不能救跨语言？**

- 治**随机性失败**（跳字、截断、句尾被吞）——**有效**，换个 seed 能捞到好的。
- 治**系统性失败**（音素映射错）——**无效**。自训 s1 那版三档 beam 输出完全一致，
  说明这个错是稳定的；多采样只会在同一个错误分布里打转。
  跨语言必须换配置（`gptMode=base`），不是换运气。

### 4.22 ★「读法对、语气不对」：s1 管节奏，s2 管音色，而 cut5 在偷偷加长停顿

4.19 解决的是「音念错了」。但换成底模 s1 之后，中文**读音**正常了，
**语气结构仍然是日语的** —— 用户的原话是「读法没问题，但语气结构是日语的、有训读色彩」。
这是两个不同层面的问题，4.19 的方案管不到这一层。

#### (1) 先纠正一个误判：s2 不负责节奏

同一段 44 字中文，固定参考音频与采样参数，只换 s1 / s2：

| 组合 | 时长 |
|---|---|
| 底模 s1 + 底模 s2 | 12.18 s |
| 底模 s1 + **自训** s2 | **12.18 s** |
| **自训** s1 + 底模 s2 | **11.42 s** |
| **自训** s1 + 自训 s2 | **11.42 s** |

**时长由 s1 决定，与 s2 完全无关**（s2 换了，时长精确到 0.00 不变）。
s1 是「文本音素 → 语义 token」的模型，它输出的 token 序列长度直接决定每个字的
时长分配与停顿位置 —— 也就是**断句、重音、语气结构**都归它管。
自训 s1 只见过 27 分钟日语，它给出的节奏因而少 6.2%。

所以「跨语言」要分两件事说：**发音准不准看 s1 选没选对**（4.19），
**语气像不像这门语言也要看 s1**。s2 只负责「用什么嗓子」。

#### (2) 真正让长文本「一顿一顿」的，是分段静音的叠加

`cut5` 把长文本按标点切句分别合成，每段音频**尾部自带约 0.9 秒静音**
（模型从参考音频那里学来的「说完留白」），上游再在段间插入
`fragment_interval`（默认 0.3 s）。两者叠加，实测：

| | 总长 | 停顿数 | 停顿总长 | 静音占比 | 停顿序列 |
|---|---|---|---|---|---|
| 修复前 | 12.18 s | 5 | 5.26 s | **43%** | 0.56 / 1.20 / 1.26 / 1.04 / 1.20 |
| 修复后 | 9.36 s | 5 | 2.62 s | **28%** | 0.88 / 0.26 / 0.36 / 0.24 / 0.88 |

**12 秒里有 5.3 秒是静音，每个句间停顿 1.2 秒** —— 听感就是逐句往外蹦；
再叠加「每句独立合成 ⇒ 每句语调都是从零起、到零收」，就非常像外国人念汉文。

修法在 `py/gsv_infer.py`：用 `return_fragment=True` 拿分段，逐段
`trim_head` / `trim_tail` 掉留白，再按 `--gap`（默认 0.22 s）拼回去。
不要用上游的 `fragment_interval` 直接调小 —— 它只减少插入的那 0.3 s，
段尾那 0.9 s 仍在。

#### (3) 音色：底模零样本已经够，fine-tune 的增益远小于它的代价

用 ERES2NetV2 说话人向量做跨语言相似度，先校准两个基准：

| 对照 | 余弦相似度 |
|---|---|
| 同说话人（芳乃语料内部真实录音） | **0.784**（0.700~0.866） |
| 异说话人（CosyVoice 中文女声） | **0.473** |
| 底模 s2 + 芳乃参考（**完全没训**，zero-shot） | **0.797** |
| 自训 s2 e8（776 步） | **0.833** |

底模零样本的 0.797 **已经落在「同说话人」区间内**，fine-tune 只再涨 0.036。
也就是说：**为了 4.5% 的音色相似度，付出了日语化的代价**，这笔交易并不划算。
（这不否定 fine-tune 的另一个价值：音色**稳定性** —— 零样本对参考音频敏感，
换一条参考音色会飘。要稳定 + 中文韵律，得让 s2 见过中文，见 (4)。）

#### (4) 试过但**不成立**的路：s2 权重线性插值

既然自训 s2 是从底模初始化的，直觉上可以插值 `θ(α)=(1-α)θ_base+αθ_ft`
在「音色像」和「调域完整」之间滑。实测**不单调**：

| α | 0.00 | 0.30 | 0.50 | 0.70 | 1.00 |
|---|---|---|---|---|---|
| F0 跨度中位数（半音） | 10.66 | 9.24 | 9.58 | 10.10 | 8.58 |

差异量级和「换一段文本」的波动（同一权重 7.0~12.9）相当，插值没有可用的中间态。
VITS 的音色与韵律纠缠在同一批参数里，**参数平均不是语义平均**。
（顺带：`enc_q.*` 共 103 个参数只在训练用，上游 `savee()` 会剥掉，
插值时按「底模原值带过」处理，不能当成 key 不一致报错。）

#### (5) 方法论教训：F0 统计量判不出「像不像这门语言」

一开始想用 F0 的跨度 / 标准差 / 双峰度来量化「日语腔」。用 16 条日文语料
与 6 条中文语料做池化基准，两者**几乎重合**（跨度 11.07 vs 11.10，标准差 3.56 vs 3.48）。
换成「音节时长离散度」才有区分（0.458 vs 0.627），但对合成音频又不稳定。

原因是：**这些统计量对「句间 1.2 秒大停顿」「每句语调重新起头」完全不敏感**，
而后者恰恰是人耳第一时间听出来的东西。教训是 ——
**先想清楚「人耳到底听到了什么」，再去挑指标；指标挑错了，实验做得再干净也是空的。**
（另外：单条 4 秒音频的 F0 跨度方差极大，任何结论都必须多文本重复测量取中位数，
否则会得出 α=0.7 突然回弹这种假象。）

#### 工具层对应

- `gptMode` 默认改为 **`auto`**：读数据集 `list.txt` 的主语言，
  与目标语言不一致就自动用底模 s1，并在渲染里说明判据（`s1 选择: 训练语料 ja → 目标 zh，跨语言，用底模 s1`）。
  仍然可以强制 `trained` / `base`。
- `gsv_infer.py` 新增 `--gap`（段间静音，默认 0.22）与 `--no-trim`（排障用），
  分段首尾静音裁剪**默认开启**。
- `test/f0_prosody.py`（韵律量化）、`test/soup_s2.py`（权重插值）、
  `test/prosody_matrix.py`（热切换权重做重复测量）留作回归与复现用。

#### 还没解决的

底模 s2 的中文韵律好但音色会飘，自训 s2 音色稳但韵律日语化。
**要同时拿到，必须让 s2 在训练时见过中文** —— 即「芳乃日文语料 + 中文语料」混合训练 s2，
或者先拿音色再用中文语料低 lr 纠一遍。本机目前没有可用的中文单说话人语料，
这一步未做。

### 4.23 ★「音节读得太快」：speed_factor 是 latent 插值，不是重采样

4.22 修完停顿之后，剩下的反馈是：**停顿对了，但每个字的音节本身还是短**。

量化后才看清：同一段 46 字中文，含停顿总时长 9.36s ⇒ **4.92 字/秒**。
中文散文朗读是 3.8~4.2，新闻播报约 5.0 —— 也就是这个模型一直用**播音速度**念散文，
自然听着赶。而「有声段」只占 92%（停顿已经裁好），所以问题不在停顿，在音节时长
（0.143 s/字，正常约 0.19~0.22）。

#### 根源

s2 的时长分布完全来自它的训练语料。芳乃的语料是 galgame 台词，日语语速本来就比中文快
（mora 约 0.12~0.14 s），模型把这个节奏原样搬到中文上。

#### 关键判断：`speed_factor` 到底会不会变调？

一开始我以为会。因为 `TTS.py` 里有这么一段：

```python
upsample_rate = math.prod(self.vits_model.upsample_rates) * (2 / speed_factor)
```

改采样率 = 重采样 = 变调，看起来铁证如山。**但这段 upsample_rate 是拿去做切片边界计算的**
（`audio_frag_idx = pred_semantic.shape[0] * 2 * upsample_rate`），不是采样率参数。

真正起作用的是 `module/models.py:259`：

```python
if speed != 1:
    y = F.interpolate(y, size=int(y.shape[-1] / speed) + 1, mode="linear")
```

作用在 **latent 序列**上，改的是序列长度，波形采样率不变 ⇒ **纯时长缩放，不改音高**。

实测验证（同一文本、同一权重、同一 seed，只改 speed）：

| speed | 总长 | s/字 | 字/秒 | F0 中位 | ΔF0 |
|---|---|---|---|---|---|
| 1.00 | 9.36s | 0.203 | 4.92 | 227.8Hz | 0 |
| 0.85 | 10.93s | 0.238 | 4.21 | 223.9Hz | −1.7% |
| 0.75 | 12.22s | 0.266 | 3.77 | 225.2Hz | −1.1% |
| 0.65 | 13.96s | 0.303 | 3.30 | 222.6Hz | −2.3% |
| 0.55 | 16.13s | 0.351 | 2.85 | 222.6Hz | −2.3% |

F0 偏移在 −1~−3%，和 pyin 本身的帧间抖动同一量级 ⇒ **没有变调**。
时长与 speed 成严格反比（9.36 / 0.85 = 11.01 ≈ 10.93），这是纯缩放的另一个佐证。

> 教训：**`speed` 这个词在同一个文件里可能指两件事。** 判断「会不会变调」要一直追到
> 真正改变波形的那一行，而不是看到采样率变量就下结论。

#### 工具层对应

- `src/config.js` 新增 `LANG_SPEED` 与 `resolveSpeed(lang, explicit)`：
  `zh 0.85 · en 0.9 · ja 1.0 · ko 1.0 · yue 0.85`。
  日文不调，因为训练语料就是日文，1.0 才是它的自然语速。
- `tts_infer` 的 `speed` 参数默认值从「不传」改成**按目标语言自动取**，
  渲染里会打印 `语速: 0.85（zh 默认）` 和 `语速 4.21 字/秒（正常朗读）`。
- `gsv_infer.py` 的 `--speed` 默认改为 `0`（= 按 `--lang` 自动），
  输出 JSON 增加 `speed` 与 `charsPerSec`，脚本单独用也不会回到老行为。
- 顺带修一个同类静默 bug：`targetLang` 取的是 `c.lang`，而配置字段是 **`c.language`**。
  `c.lang` 恒为 `undefined`，靠 `|| 'zh'` 兜底 —— 中文场景看不出问题，
  日文/英文配置会被误判成跨语言。同 4.22 的 `findVoice` 一样，都是「字段名写错 + 兜底掩盖」。

#### 选哪个值

- **中文散文/朗读**：0.85（默认）
- **更舒缓、适合长句抒情**：0.75
- **低于 0.6** 开始拖沓，且 latent 插值过多会让辅音发散

### 4.24 ★★ 一次「模型像霸天虎」的误判：peak 和 rms 都正常，音频却已经是方波

4.23 的四档语速对照音频发出去后，反馈是：**「失真严重、尖音非常尖锐，ASR 都读不出来」**。

第一反应是怀疑 latent 插值在大比例拉长时出了机械伪影。于是去查指标 ——
谱平坦度还「随拉长下降」（看着更干净）、15~45Hz 调制占比持平，一切正常。
**差点就顺着这个方向去写结论了。**

真正拦住这一步的是一个最笨的数：**数音频里有几个不同的取值**。

```
sp100.wav   样本 299401   min=-32767  max=32767   唯一值个数 = 3
            最高频取值: 32767(140538次)  -32767(124304次)  0(34559次)
            |x| >= 32700 的比例: 88.5%
```

**整段音频只有 3 个取值** —— 这是一个二值方波。方波的谐波按 1/n 衰减到很高频率，
所以「尖音尖锐」；波形信息几乎全丢，所以「ASR 读不出来」。而 `peak = 1.0`、
`rms` 正常、时长正常、甚至连 F0 中位数都还能测出来（方波的基频还在），
**所有既有检查全部放行**。

#### 根因（一行）

`tts.run()` yield 出来的 chunk 是 **int16**。测试脚本里写了：

```python
a = np.clip(np.asarray(audio), -1, 1)          # ← audio 是 int16
a = (a * 32767).astype(np.int16)
```

`np.clip(int16_array, -1, 1)` 把 −32768~32767 全部压成 {−1, 0, 1}，再乘 32767
就是满幅方波。`gsv_infer.py` 主流程有 `if audio.dtype != np.int16` 保护，
所以走插件那条路一直是对的 —— **坏的只有实验脚本**。

> 教训一：**`np.clip(x, -1, 1)` 之前必须先确认 dtype。** 这是 PyTorch/音频代码里的
> 经典陷阱：float 音频归一化后是 [−1,1]，但 int16 的「1」是 −32767 的邻居。
>
> 教训二：**「指标正常」不等于「音频正常」。** peak / rms / 时长 / F0 这些二阶统计量
> 对方波完全不敏感，甚至会给出「频谱更干净」这种反向结论。判断音频是否被毁，
> 最直接的量是**取值分布**（唯一值个数、贴顶比例），不是能量统计。
>
> 教训三：**当听感和指标打架时，先怀疑自己的测量代码。** 这次是用户先听出了
> 「霸天虎」，指标却在说「没问题」——如果相信指标，会得出「模型有机械伪影」
> 这种完全错误的结论，然后去改一个根本没坏的地方。

#### 已加防护

`gsv_infer.py` 的产物自证从「有时长、有声音」扩成三条，任何一条不过直接判失败：

```python
uniq = int(np.unique(audio).size)
clip_ratio = float((np.abs(audio.astype(np.int32)) >= 32700).mean())
if uniq < 64 or clip_ratio > 0.05:
    → 失败："音频已失真：唯一取值仅 N 个，X% 样本顶到满幅"
```

输出 JSON 同时带 `uniqValues` / `clipRatio`，实验脚本可以直接断言。

#### 重测结论（干净音频）

| speed | 字/秒 | ASR 回读 | avgLogprob |
|---|---|---|---|
| 1.00 | 4.92 | 全对 | −0.070 |
| 0.85 | 4.21 | 「荷塘」→「核桃」 | −0.097 |
| 0.75 | 3.77 | 「荷塘」→「河塘」 | −0.115 |
| 0.65 | 3.30 | 全对 | −0.100 |

46 字里最多错 1 字，且是同音混淆（荷塘/河塘/核桃），**四档全部通过 ASR 门**。
所以 4.23 的时长与 F0 结论不受影响，模型本身没有任何问题。

### 4.25 ★★★「念出来像湖南口音」：不是音素、不是声调，是参考音频的语言

语速调到 0.75~0.85 之后，用户反馈「读音有点湖南口音」。这句话把范围收得很窄，
但**先后两条直觉都是错的**，值得完整记下来。

#### 排除一：不是音素被训坏

最直觉的解释是「s2 只用日文学，丢了中文的音素区分度」（zh/ch/sh、n/l、-n/-ng 日语都没有）。
用五组最小对立对分别合成自训 s2 / 底模 s2，再比 ASR 的字错误率：

| 组 | 底模 s2 CER | 自训 s2 CER |
|---|---|---|
| 四是四，十是十 | 25.0% | 25.0% |
| 老刘买了牛奶 | 84.6% | **76.9%** |
| 湖南的湖水 | 38.5% | 38.5% |
| 人民的心很明亮 | 28.6% | **7.1%** |
| 人生若只如初见 | 80.0% | **66.7%** |

自训 s2 **四平一胜**，不存在退化。而且这些短句的绝对 CER 高得离谱（84.6%），
说明 ASR 在无上下文的孤立短句上本身就不可靠，**不能拿它当判据**。

#### 排除二：不是声调被压平

理论上最像「方言」的东西是字内音高轮廓（普通话 1 声平、2 声升、4 声降）。
写了 `test/tone_analysis.py`：ASR 取字级时间戳 → pyin 提 F0 → 字窗内等分三段 →
用 `drift = 末−首`、`dip = 中−max(首,末)` 判调型。

结果自训 s2 的「2 声 drift − 4 声 drift」是 **−1.75**，看起来「2 声被读成降调」，
很像证据。但同一指标跑 CosyVoice 标准普通话是 **−1.78** —— 母语模型一样为负。

原因是语音学常识：**所有音节末尾都有 F0 下倾（final lowering）**，且 pyin 在字尾清音处
不可靠，`末−首` 天然偏负。这个指标量的是我的测量偏差，不是模型的调值。

> 教训：**任何「听起来像 X」的假设，先拿母语模型跑同一条指标**。
> 没有基线的绝对值毫无意义——4.23 的 F0 池化指标也是这么失效的。

#### 真因：参考音频的语言（2×2 对照）

GPT-SoVITS 的推理是 **in-context learning**：`ref_audio` + `prompt_text` 不是「音色样本」，
而是「这样发音」的示范。参考是芳乃的**日文台词**，模型看到的是日语怎么把音素变成声音，
于是把日语的**音节时长分配规律**套到中文上。

四格对照（同一句、同 seed、同 speed=0.8，唯一变量是 s2 权重 × ref 语言）：

| 配置 | CER | 时长 | 字时长 CV | avgLogprob |
|---|---|---|---|---|
| 自训 s2 + 日文 ref | 2.2% | 13.92s | **1.172** | −0.085 |
| 自训 s2 + 中文 ref | **0.0%** | 13.24s | **0.504** | −0.062 |
| 底模 s2 + 日文 ref | 4.3% | 13.98s | 1.156 | −0.094 |
| 底模 s2 + 中文 ref | 2.2% | 13.26s | 0.494 | −0.066 |

- **s2 权重几乎无影响**：同一个 ref 下，trained 与 base 的时长差 0.00~0.06s，CV 差 0.01~0.02。
- **ref 语言决定一切**：CV 1.17 → 0.50（降 57%），CER、avgLogprob 同步变好。

`字时长 CV` 是这里唯一有效的量：它衡量「每个字分到的时间有多不均匀」。
普通话有轻声和重读，CV 有正常范围（CosyVoice 是 0.67）；CV 1.17 意味着有的字被拖很长、
有的被压到几乎没有——这就是「音节松紧不像中文」的直接来源，听感上被归为方言腔。

#### 解法：中文 ref 生成 + DDSP-SVC 换音色

问题在于「中文 ref 的音色不是芳乃」。本机已有芳乃的 DDSP-SVC reflow 模型
（`02_模型推理_DDSP-SVC-6.2/.../exp/reflow-senren-yoshino/model_20000.pt`），
音色转换用的是 contentvec 特征，**与语言无关**，正好接得上：

```
中文 ref（任意标准女声）──GPT-SoVITS──> 标准普通话 ──DDSP-SVC(芳乃)──> 芳乃音色 + 中文韵律
日文 ref（芳乃原声）  ──GPT-SoVITS──> 日语腔中文 ──DDSP-SVC(芳乃)──> 芳乃音色 + 日语腔（反证）
```

参数选择（`--infer_step` 与 `--key` 都要给，前者默认 auto=50）：

| VC 配置 | CER | F0 中位 |
|---|---|---|
| 50 步 | 8.7% | 263Hz |
| 100 步 | 8.7% | 265Hz |
| **100 步 + `--key=-1`** | **4.3%** | **248Hz** |
| 转换之前（参照） | 0.0% | 265Hz |

芳乃原声 F0 中位是 **245.4Hz**。降一个半音把 265 拉到 248，正好落进模型训练音域，
CER 从 8.7% 回到 4.3%（只剩「荷塘」→「河滩」一处近音）。**音高不对齐时，
DDSP 声码器工作在音域边缘，失真会明显变大**——这是之前 8.7% 的主因，不是步数不够。

失真检查（转换版 8k+ 能量 1.14%、尖峰 0、峰值 0.547、谱平坦度 0.149），
比日文 ref 那条（3.12% / flat 0.107）略噪一点，但仍远优于「日文 ref 转音色」那条
（flat 0.323，因为韵律乱 + 音域不匹配双重叠加）。

#### 代价与限制

1. **多一跳 VC**：DDSP-SVC 是 44.1kHz 声码器重建，会带来轻微「电子味」，
   CER 从 0.0% 涨到 4.3%。
2. **需要一段中文参考音频**：不要求是芳乃，任意发音标准的女声都行（这里用 CosyVoice 生成）。
   这一步不能省——它才是「中文韵律」的来源。
3. `--key` 的值依赖两个音色的音高差：换成别的参考音频要重测 F0，不能照抄 −1。

> **★ 这条 VC 路线已降级为实验分支并放弃（2026-10-19）。**（开发期代码不随本仓库分发）
> 它不是主链路的一环，插件任何工具都不会调用它。
> 时间轴与感知的账见 §4.26；**放弃的根本理由见 §4.27（发音方式即角色特质）**。
> **主链路不变：`tts_infer` 只做 GPT-SoVITS，日文参考 + 32kHz 单段直出。**

### 4.26 ★★「转换之后太长太慢」：时间轴没动，动的是采样率和调门

4.25 交付了四条对照音频，推荐的是 `03 中文参考 + 转芳乃音色`。反馈是一句话：
**「这一轮转换就导致输出录音太长太慢了」**。

第一反应会是「VC 把音拉长了」。**测出来是错的**：总时长 13.522s → 13.526s，差 **4 毫秒**。

#### 逐段对账：时间轴逐帧一致

用 10ms 帧能量 + `max−30dB` 阈值切段，再把 02（转换前）与 03（转换后）逐段对齐：

| | 02 转换前 | 03 转换后 |
|---|---|---|
| 总时长 | 13.522s | 13.526s |
| 有声段合计 | 10.80s | 10.58s |
| 段长 | 0.88 / 1.55 / 2.29 / 1.11 / 1.60 / 1.59 / 1.78 | 0.83 / 1.52 / 2.29 / 1.12 / 1.15+0.28 / 1.61 / 1.78 |
| 段间停顿 | 0.22 / 0.59 / 0.52 / 0.19 / 0.51 / 0.61 | 0.26 / 0.61 / 0.52 / 0.20 / 0.16 / 0.51 / 0.58 |

段长逐段差 ≤ 0.05s，段间停顿同一量级。**VC 没有改时间轴**（03 多切出的一段 0.28s 是能量凹陷，
不是新停顿）。所以「太长」这个词，指向的不是时长。

#### 两个真因

**(1) 采样率契约破了 —— 这是真 bug。** `tts_infer` 出料 32000Hz，DDSP-SVC 的声码器是 44100Hz。
03 直接落盘成 44.1k，任何按 32k 解读它的环节（拼接、混音、按帧率对齐）都会**慢 1.378 倍**：
13.53s 听成 18.6s。用户听到的「太长」很可能就是这个比例关系。

**(2) 降调听起来像减速。** `--key=-1` 把 F0 从 265Hz 压到 248Hz（−6.4%，约一个半音，
为贴近芳乃原声 245Hz）。时长不变而降调，人耳会读成「更沉、更拖、更慢」。

两者叠加，就是「太长太慢」——而它们**都不是时间问题**，所以改语速、改 speed 参数永远修不好。

#### 处理：不修，隔离

修采样率只要一行 `resample_poly`，但第二个因是**音色的固有代价**：要芳乃的音域就必须降调，
降调就必须接受拖沓感。而这条路线唯一增量是「音色像芳乃」——主链路换个中文 ref 已经拿到「无口音」，
不值得为音色再叠一次生成式重合成。

于是按用户决定，把它**整条移出主链路**：

- 代码被拆成独立 CLI（开发期产物，**插件任何工具都不会调用它**，也不在本仓库）。
- 出料强制 `--sr 32000`，并对齐 32k 契约；结尾打印 `drift=±Xms`，超 60ms 返回码 3。
- 四条对照音频留在开发期工作区，未随仓库分发。
- 主链路 `tts_infer` 一字未改。

重跑验证：`02 → 03b`，`13.522s@32k → 13.526s@32k`，`drift=+3ms`，`uniq=16233`（无方波）。

> 教训：**用户的听感描述（「太长太慢」）指向的是感知，不是物理量。**
> 先去测时长会得到「没变」的结论，然后很容易错误地把用户判成听错。
> 正确顺序是：时长 → 采样率 → 音高 → 音量包络，**逐层查契约**，
> 因为「感知到的变慢」可以由采样率错配和降调各解释一半。

### 4.27 ★★★ 目标换向：发音方式是角色特质，不是待修的缺陷

用户对 VC 分支的最终判断不是「慢」，而是一句更根本的话：

> **「发音方式本来就是角色特质非常重要的一部分，拿 VC 转感觉丢很多信息，
> 暂时不追求标准中文吧，以 [语速 0.85 / 4.2 字秒] 这个版本作为新基线。」**

这句话把优化目标换了。4.22~4.26 做的所有事——换中文 ref、加 VC 补音色——都在追「像标准普通话」。
指标确实全线变好（CER 2.2% → 0.0%，字时长 CV 1.17 → 0.50），**但人已经不是那个人了**。

#### 错在哪

角色特质 = **音色 + 发音方式**。两条补救路线各自破坏了其中一半：

| 路线 | 拿到的 | 丢掉的 |
|---|---|---|
| 换中文 ref | 标准普通话韵律 | 角色的发音方式（换成了别人的咬字习惯） |
| DDSP-SVC 换音色 | 芳乃的音色 | 发音方式（contentvec 只保留内容特征，音高、咬字力度、语速分布全丢） |

而这两样恰恰是同一件东西的两面：**「像方言」不是失真，是这个角色说中文时的样子**。
把它修掉，剩下的就是一个音色相似、但说话习惯不属于任何人的声音。

> 所以 4.25 那张「CV 1.17 → 0.50」的表，正确读法不是「变好了」，
> 而是**「变成另一个人了」**。指标只能证明差异，不能替你决定哪个方向是对的。

#### 新基线（`src/config.js` 的 `BASELINE`）

| 项 | 值 | 为什么 |
|---|---|---|
| 参考音频 | 芳乃日文原声 `yos003_023.wav` | **发音方式的示范来源**，不能换 |
| 参考台词 | ですが、絶対に何とかしますから。私に任せて下さい | 必须与参考音频同语言，否则塌成静音 |
| s2 | 自训 `yoshino_e8_s776.pth` | 音色 |
| s1 | **底模** `s1v3.ckpt` | ja 语料 → zh 目标 = 跨语言，自训 s1 的音素映射被训窄 |
| 语速 | 0.85 | 实测 4.21 字/秒（1.0 是 4.92 的播报速度） |
| 分句 | cut5 + 段尾裁剪 + `gap 0.22` | 句内停顿 0.24~0.36s；不裁会叠到 1.2s |
| 采样 | temperature 0.6 / top-k 5 / top-p 1.0 | 8 轮欠拟合下的稳定档，1.0 时韵律会飘 |
| seed | 42 | 可复现 |

#### 顺手修掉一处静默不一致

py 端默认是 `temperature=1.0 / top-k=15`，而基线是 `0.6 / 5`。
也就是说：**之前「不传参数跑一遍」得到的东西，从来不是用户听过并认可的那条**。
现在 `tts_infer` 不传采样参数时直接取 `BASELINE`，渲染里会打印
`采样: temperature=0.6 · topK=5（基线 2026-10-19 芳乃·日文腔中文）`。

#### 落地

| 位置 | 内容 |
|---|---|
| `src/config.js` | `BASELINE` 常量 + `pickGptMode()` 纯函数（从 index.js 抽出，便于单独核对） |
| `src/index.js` | 采样默认取基线；渲染标注「基线」 |

基线音频本身**不随仓库分发**（涉及角色声音）。要重建回归比对，用你自己的参考音频按
`BASELINE` 里的参数合成一条，再拿后续改动逐样本比（本项目开发期用的判据是 `corr > 0.999`）。

#### 什么时候才再谈「标准中文」

只有一种情况：**拿到同一角色的中文语料**，用角色本人的中文录音去混训 s2 / s1。
发音方式由他自己的中文录音提供，既不换人也不转音色。
换 ref 和 VC 都是绕道，**绕道必丢信息**——这是这一轮的结论。

### 4.28 ★★★ 训练轮数不是瓶颈：s2 在 1 轮就饱和了

用户问「本地模型充分训练能不能解决问题」。没有多训一轮就答了——因为
`e1_s97 / e4_s388 / e8_s776` 三个 checkpoint 本来就在本机，能直接做**轮数曲线**。

**设计**：固定除 s2 权重外的一切（同文本 / 同日 ref / 同 seed 42 / speed 0.85 /
cut5 / temp 0.6 / top-k 5），另加两个端点做标定——`BASE` 是同权重再跑一次（噪声地板），
底模 s2 是换模型（阴性对照）。

| 权重 | CER | 总长 | 字/秒 | 字时长 CV | F0 | 谱距离 |
|---|---|---|---|---|---|---|
| e1_s97 | 4.3% | 10.963s | 4.44 | 0.875 | 227.8 | 0.0005 |
| e4_s388 | 4.3% | 10.908s | 4.47 | 0.871 | 226.5 | 0.0005 |
| **e8_s776** | 4.3% | 10.931s | 4.43 | 0.879 | 223.9 | 0 |
| BASE（重跑） | 4.3% | 10.931s | 4.43 | 0.879 | 223.9 | 0.0000 |
| 底模 s2 | — | 10.790s | 4.26 | — | — | 0.0014 |
| 芳乃真人 | — | — | — | — | — | 0.0017 |

**8 倍训练量（97 → 776 步）换来的全部变化，都在噪声内**：CER 一字不差，
字/秒 差 0.7%，CV 差 0.8% 且非单调；谱距离 0.0005，只有「换个音色模型」的 1/3。

#### 为什么必然是 0.5%，而不是 50%

两个模块分工不同：**s1 决定「念成什么、在哪里停、重音落哪」，s2 只负责把它渲染成波形。**

数据里有个直接证据：三个不同轮数的权重，**错读位置完全一样**——`荷塘` 全被读成
`河道`/`核桃`。发音决策不归 s2 管，所以**换 s2 权重不会改变「像不像日语」**。

杠杆差距：

| 变量 | 字时长 CV 变化 |
|---|---|
| s2 轮数 1 → 8（8 倍） | **0.5%** |
| ref 语言 ja → zh | **130%**（1.17 → 0.50） |

#### 反直觉推论：把自训 s1 训透，方向是反的

自训 s1 学的是那 383 条**日语**语料的断句、重音、停顿习惯。
训得越充分，日语韵律学得越牢，念中文只会更日语化。
所以跨语言时 `gptMode=auto` 必须选底模 s1——这条不是保守，是方向正确。

#### 那还该往哪使劲

1. **ref 音频本身**（零训练成本）——唯一还没试过、且不需要训练的杠杆。
   基线用的 ref 情绪较满，in-context 会把那种起伏搬过来；换一段语速稳、语调平的
   芳乃台词，腔调会变。
2. **语料量**（27 分钟偏少）——影响音色覆盖与稳定性，**不影响腔调**，因为腔调不归 s2。
3. **中文语料混训**——唯一能真正改腔调的路，代价见 §4.27，已裁定放弃。

完整数据与复现脚本留在开发期工作区（不随仓库分发）；四个环境坑记在这里：
16kHz 假设 / HF 离线 / cublas DLL / `--out` 相对路径。

### 4.20 日语文本的 UNK：732 项符号表之外的一切都被降级

`symbols2.py` 的符号表是 732 项。`japanese.py` 的 g2p 会输出两类不在表里的东西：

1. `「」『』～―（）()` 这类无音值符号 —— pyopenjtalk 不把它们转成音素，直落表外；
2. `#`，声调短语边界（accent phrase border）—— 每处词边界都有一个。

`cleaner.py` 里那行 `phones = ["UNK" if ph not in symbols else ph for ph in phones]` 把它们全变成 `UNK`。
后果不是读错音，而是**所有词边界共享同一个 embedding**，模型分不清「短停」和「连读」：实测 UNK 只影响节奏
（PER p=0.30、音素回收 p=0.12 都不显著），净发声时长被拉长约 7%。

`tts_patch_text` 打的就是这个补丁（两处：剥符号 + 过滤 `#`），带三条约束：

- **不能改符号表**：732 → 733 会让底模 embedding 维度不匹配，等于要重训底模；
- **打前核符号表**：如果哪天上游把这些字符收进表里，剥离就会删掉**有音素**的符号——那比 UNK 更糟。
  工具发现冲突会直接拒绝，而不是照打；
- **打了必须重训**：实测「只打补丁不重训」是负收益（PER 0.197 → 0.236），因为推理端文本条件变了、
  权重还是旧条件训的。给旧权重做对照推理要设 `GSV_LEGACY_UNK=1` 还原上游行为，否则 A/B 不成立。

代价也说清楚：剥符号那一步在 383 行里有 7 行（1.83%）读音会变，其中 4 例把
「有地さん（ありちさん）」读成「ゆうちさん」——那是 pyopenjtalk 在短句上重新断词造成的，
换成顿号修不好（真正的切分点是 `…` 而不是引号）。

按这轮实测，**文本侧只贡献约 5% 的 PER 改善，音频侧贡献 95%**。只能改一处的话，先改音频怎么切。

## 6. 宿主进程回收与长任务的建议

`tts_run` 用 `detached + unref` 启动训练，正常情况下训练进程独立于插件存活。
但某些沙箱 / 宿主实现会在**调用结束后回收整棵进程树**，表现为：
`tts_run` 返回了 pid，但几秒后进程消失、日志 0 字节。

判断方法：`tts_status` 会同时报「进程存活」与「权重目录真实文件」。
如果进程反复消失而权重没动，改用长活会话启动（把 `tts_run` 与其后轮询放在同一个一直不退出的进程里），
或用系统级启动器（本机实践中 `Win32_Process.Create` 比 `Start-Process` 更不容易被回收）。

## 9. 与 `dsh-train-pipeline` 的关系

本插件**不依赖**它，也**不改动**它。两者共用：

- 同一份解包语料（`dsh-train-pipeline` 的 `train_unpack` 产物）
- 同一个 `songRoot`（`DSH_COVER_ROOT`）
- 同一套 `src/config.js` / `src/execution.js` 的设计约定

关键差异在于**台词**：`dsh-train-pipeline` 的 `build_dataset.py` 出料时把
`r.get("text")` 丢掉了（SVC 用不上），本插件把这份被丢掉的资产接回来，
并因此**不需要 ASR 回标**。
